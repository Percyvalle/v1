# Cloudweb

Монорепозиторий Twitch-бота: ИИ-компаньон чата и анти-спам модерация в
одном процессе, плюс веб-панель управления ими. Всего процессов два —
бот и панель.

```
apps/twitch-bots/   ИИ-бот: читает Twitch IRC, отвечает, голосовой ввод
apps/cigilbot/      Анти-спам модерация: детекторы, кластеризация, движок
apps/panel/         Веб-панель обоих продуктов (порт 8766), общий вход
docs/               Планы и архитектура
var/                Рабочее состояние: БД, логи, pid-файлы (вне git)
_archive/           Остатки старой per-channel модели (вне git)
```

`apps/` — только исходники, `var/` — только данные. Раньше БД, логи и
pid-файлы лежали прямо в корнях проектов вперемешку с кодом; из-за этого
путь «корень проекта» незаметно означал сразу и место кода, и место
конфига, и место БД — и разошлось это только когда панель переехала.

## Как связаны части

Модерация работает внутри процесса бота — через очередь в памяти, без
файлов-посредников и без HTTP:

```
apps/twitch-bots/main.py                  cigilbot/pipeline.py (тот же процесс)
  читает Twitch IRC                         ModerationHub: движок на канал
  hub.submit(event)        --queue-->       разбирает в фоне, пишет verdict
  (возвращается сразу)                       в mod.<broadcaster_id>.db
```

Раньше между ними стояла граница процессов: `main.py` писал каждое
сообщение в таблицу `mod_inbox` на диске, а отдельный процесс на каждый
канал читал её в фоне. Теперь очередь в памяти, а `submit()` по-прежнему не
ждёт: чтение чата не должно оплачивать запись в SQLite и поход в Helix.

Цена этого решения названа прямо: очередь больше не переживает падение
процесса и не безгранична. Раньше при вставшей модерации сообщения копились
на диске и не терялись; теперь при переполнении они **отбрасываются** —
ждать нельзя, иначе тормоза модерации дойдут до чтения чата. Каждая потеря
считается и попадает в лог.

## Почему панель — отдельный процесс

Всё остальное свели в один, а её оставили снаружи, и по обратной причине:
панель ничего не считает и не исполняет. Она пишет `desired_state`,
паттерны и Attack Mode в те же БД, откуда их читает бот. Поэтому её можно
уронить, перезапустить или просто не открывать — модерация этого не
заметит. Так было не всегда: supervisor жил внутри панели, и её закрытие
останавливало перезапуск упавших консьюмеров.

Общими стали окружение и конфиг:

- **Один `.venv` в корне.** Бот импортирует и `bot.*`, и `cigilbot.*`, панель
  тоже — из двух раздельных окружений один процесс не собирается.
- **Один `.env` в корне.** Раньше в двух файлах лежали одни и те же
  `PANEL_TWITCH_*` ключи с разными значениями, потому что двум панелям на
  разных портах нужны были разные redirect URI.
- **Голос — отдельно.** `faster-whisper`/`numpy`/`sounddevice` вынесены в
  `requirements-voice.txt` (~600 МБ) и ставятся только при `VOICE_ENABLED=true`.

## Установка

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements-dev.txt   # включает requirements.txt
copy .env.example .env

# Только если нужен голосовой ввод (~600 МБ)
.\.venv\Scripts\pip install -r requirements-voice.txt
```

## Запуск

```powershell
# Панель (порт 8766) — оба экрана, и из неё же запускается бот
cd apps\panel
..\..\.venv\Scripts\python -m panel.server
```

Бот запускается кнопкой на экране Registry, либо вручную:

```powershell
cd apps\twitch-bots
..\..\.venv\Scripts\python main.py            # чат + модерация всех каналов
..\..\.venv\Scripts\python voice_main.py      # только при VOICE_ENABLED=true
```

Модерацию отдельно запускать не нужно: `main.py` поднимает движок на каждый
канал, у которого `desired_state=running`, и сам следит за изменениями.

## Состояние

Модерация работает в **SHADOW-режиме**: анализирует чат и пишет вердикты в
БД, но сама никого не банит и не таймаутит, пока владелец канала явно не
включит исполнение. Phase 1 закрыт и проверен на живых каналах
(`dobriy_yura`, `paverpapa`). Следующее по плану — Phase 2, Alerts.
